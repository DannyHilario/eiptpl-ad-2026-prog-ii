# 1.3 Funciones definidas por el usuario

*Anterior: [1.2 Funciones predefinidas](1.2-funciones-predefinidas.md) — Siguiente: [1.4 Reglas de alcance](1.4-reglas-de-alcance.md)*

Cuando C++ no trae una función predefinida para lo que necesitas, la escribes tú
mismo. A esa función se le llama **función definida por el usuario** — el tema
central de esta sesión, y la base de todo lo que sigue en el curso.

## Anatomía de una función

Toda función en C++ tiene tres momentos distintos, y es importante no confundirlos:

1. **Prototipo (declaración):** le dice al compilador que la función existe, qué
   recibe y qué regresa — sin el código que hace el trabajo. Termina en `;`.
2. **Definición:** el código real de la función, con su cuerpo entre `{ }`.
3. **Llamada:** el punto del programa donde efectivamente se usa la función.

```cpp
#include <iostream>
using namespace std;

// 1. Prototipo: le avisa al compilador que "mayor" existe antes de usarla en main()
int mayor(int a, int b);

int main() {
    int x, y;
    cout << "Escribe dos numeros enteros: ";
    cin >> x >> y;

    // 3. Llamada: aqui se ejecuta la funcion con los valores reales
    int resultado = mayor(x, y);
    cout << "El mayor es: " << resultado << endl;

    return 0;
}

// 2. Definicion: el cuerpo real de la funcion, despues de main()
int mayor(int a, int b) {
    if (a > b) {
        return a;
    }
    return b;
}
```

Puntos clave de este ejemplo:

- El **prototipo** (`int mayor(int a, int b);`) va antes de `main()` para que el
  compilador sepa que la función existe cuando la encuentre ahí. Sin el prototipo, el
  código no compilaría porque `mayor` se usa antes de estar definida.
- El **tipo de retorno** (`int` en este caso) debe coincidir entre el prototipo, la
  definición, y lo que realmente hace `return` dentro del cuerpo.
- Si una función no regresa ningún valor, su tipo de retorno es `void`, y no lleva
  `return valor;` (puede llevar un `return;` vacío para salir antes de tiempo).
- Los nombres de los parámetros en el prototipo son opcionales — el compilador solo
  usa los tipos para verificar que la llamada sea correcta. `int mayor(int, int);`
  sería un prototipo igual de válido, aunque menos claro de leer.

## Un vistazo más profundo: ¿qué hace el compilador con las funciones?

Compilar no es un solo paso: el compilador primero prepara el archivo
(preprocesado), lo traduce a instrucciones de máquina (compilación/ensamblado), y al
final **enlaza** todo para armar el ejecutable (linking). Las funciones son clave en
esa última etapa.

Cada función que escribes se traduce a un bloque de instrucciones con un nombre (un
**símbolo**). El prototipo le basta al compilador para generar el código que *llama*
a esa función — sabe cuántos parámetros manda y qué tipo regresa — aunque el cuerpo
real esté definido más abajo en el mismo archivo, en otro archivo `.cpp`, o incluso
ya compilado dentro de una biblioteca externa.

**¿Por qué solo puede existir un `main()`?** Porque `main()` es el **punto de
entrada** del programa: es la función que el sistema operativo llama primero al
ejecutar tu programa, y solo puede haber uno. Si escribes dos `main()` en el mismo
archivo, el compilador lo detecta de inmediato como "redefinition of main" (dos
definiciones con el mismo nombre en el mismo archivo, algo que nunca es válido en
C++, tenga que ver con `main` o no). Si el curso más adelante trabaja con varios
archivos `.cpp` compilados juntos, el mismo problema — dos `main()` — ya no lo
detecta el compilador al revisar cada archivo por separado, sino el **enlazador**,
al intentar armar un solo ejecutable y encontrarse el símbolo `main` repetido
("duplicate symbol"). Es el mismo error de fondo (dos puntos de entrada, ¿cuál
usar?), pero detectado en una etapa distinta según si las dos definiciones están en
el mismo archivo o no.

**¿Y las funciones que no escribiste tú, como `cout` o `sqrt`?** Cuando pones
`#include <iostream>` o `#include <cmath>`, ese header trae la *declaración* — le
dice al compilador "esto existe y es de este tipo". El código real que sabe cómo
escribir a la terminal, o calcular una raíz cuadrada, **no está en el header** —
vive ya compilado dentro de la biblioteca estándar de C++ que se instaló junto con
tu compilador. El enlazador es quien busca esa implementación y la conecta con tu
programa al final. Por eso a esta etapa se le llama *enlazado*: conecta cada llamada
a una función (la tuya, o de una biblioteca) con su implementación real, sin
importar dónde viva esa implementación.

Esto también explica por qué no puedes tener dos funciones con el mismo nombre y los
mismos tipos de parámetros en un programa: el enlazador vería dos símbolos iguales y
no sabría cuál usar.

## Alcance de una función: `extern` (por default)

Las funciones son `extern` por default — accesibles desde cualquier parte del
programa, aunque estén en otro archivo `.cpp` del mismo proyecto (esto importa más
cuando el curso llegue a programas de varios archivos; por ahora, con un solo
archivo, ya tienes ese comportamiento sin tener que escribir nada especial).

## Ejemplo 1 — tres funciones combinadas: mayor, menor e iguales

```cpp
#include <iostream>
using namespace std;

int mayor(int a, int b);
int menor(int a, int b);
bool sonIguales(int a, int b);

int main() {
    int x, y;
    cout << "Escribe dos numeros enteros: ";
    cin >> x >> y;

    if (sonIguales(x, y)) {
        cout << "Los dos numeros son iguales." << endl;
    } else {
        cout << "El mayor es: " << mayor(x, y) << endl;
        cout << "El menor es: " << menor(x, y) << endl;
    }

    return 0;
}

int mayor(int a, int b) {
    if (a > b) {
        return a;
    }
    return b;
}

int menor(int a, int b) {
    if (a < b) {
        return a;
    }
    return b;
}

bool sonIguales(int a, int b) {
    return a == b;
}
```

Nota que `sonIguales` regresa `bool` (`true`/`false`), no `int` — el tipo de retorno
se elige según qué tan bien representa lo que la función responde: aquí la pregunta
es sí/no, así que `bool` es más claro que usar `1`/`0`.

## Ejemplo 2 — una función con un ciclo adentro

Las funciones no están limitadas a una sola operación: pueden contener ciclos,
condicionales, y todo lo que ya sabes usar dentro de `main()`.

```cpp
#include <iostream>
using namespace std;

int sumaDeNNumeros(int n);

int main() {
    int n;
    cout << "Cuantos numeros quieres sumar? ";
    cin >> n;

    int resultado = sumaDeNNumeros(n);
    cout << "La suma es: " << resultado << endl;

    return 0;
}

int sumaDeNNumeros(int n) {
    int suma = 0;
    int valor;
    for (int i = 1; i <= n; i++) {
        cout << "Numero " << i << ": ";
        cin >> valor;
        suma = suma + valor;
    }
    return suma;
}
```

Aquí `sumaDeNNumeros` recibe `n`, pide `n` números por teclado (usando `cin` dentro
de la función — sí se puede), y regresa el total acumulado. `main()` no sabe ni le
importa cómo se hizo la suma internamente; solo le importa el resultado final.

*Nota:* más abajo vamos a ver que, en general, conviene **no** mezclar `cin`/`cout`
con cálculo dentro de una función. `sumaDeNNumeros` es una excepción pragmática: sin
arreglos (que se ven hasta la Etapa II) no hay forma limpia de recibir "n números"
como parámetros por separado, así que aquí se acepta leer dentro de la función.
Cuando lleguemos a arreglos, vas a poder separar la lectura del cálculo real.

## Ejemplo 3 — una función `void` (sin valor de retorno)

No todas las funciones necesitan regresar un valor. Algunas existen solo para
*hacer* algo (como imprimir), no para calcular un resultado que se vaya a usar
después.

```cpp
#include <iostream>
using namespace std;

void imprimirTabla(int numero);

int main() {
    int numero;
    cout << "De que numero quieres la tabla de multiplicar? ";
    cin >> numero;

    imprimirTabla(numero);

    return 0;
}

void imprimirTabla(int numero) {
    for (int i = 1; i <= 10; i++) {
        cout << numero << " x " << i << " = " << (numero * i) << endl;
    }
}
```

`imprimirTabla` es `void`: no hay `return valor;` en su cuerpo, y en `main()` no se
guarda ningún resultado de la llamada (`imprimirTabla(numero);` es una sentencia
completa por sí sola, no una expresión que se asigne a algo).

## Ejemplo 4 — aíslas errores (y reutilizas en contextos distintos)

Una función que hace descuentos sobre el precio de un boleto de cine, usada en tres
situaciones distintas de la misma taquilla (no son 3 copias del mismo caso, son 3
casos distintos que comparten la misma fórmula):

**Sin función** — la fórmula del descuento repetida 3 veces, con un error metido a
propósito (suma el descuento en vez de restarlo):

```cpp
#include <iostream>
using namespace std;

int main() {
    double precioBoleto = 80.0;

    double precioEstudiante = precioBoleto + (precioBoleto * 20 / 100);
    cout << "Precio con descuento de estudiante (20%): $" << precioEstudiante << endl;

    double precioTerceraEdad = precioBoleto + (precioBoleto * 30 / 100);
    cout << "Precio con descuento de tercera edad (30%): $" << precioTerceraEdad << endl;

    double precioPromoMartes = precioBoleto + (precioBoleto * 50 / 100);
    cout << "Precio con promocion de martes (50%): $" << precioPromoMartes << endl;

    return 0;
}
```

Con el error, esto imprime `$96`, `$104` y `$120` — un "descuento" que en realidad
sube el precio. Para corregirlo hay que encontrar y cambiar **las 3 líneas**, una
por una, con el riesgo de dejar alguna sin corregir.

**Con función** — la misma fórmula, pero escrita una sola vez:

```cpp
#include <iostream>
using namespace std;

double calcularPrecioConDescuento(double precio, double porcentajeDescuento);

int main() {
    double precioBoleto = 80.0;

    double precioEstudiante = calcularPrecioConDescuento(precioBoleto, 20);
    cout << "Precio con descuento de estudiante (20%): $" << precioEstudiante << endl;

    double precioTerceraEdad = calcularPrecioConDescuento(precioBoleto, 30);
    cout << "Precio con descuento de tercera edad (30%): $" << precioTerceraEdad << endl;

    double precioPromoMartes = calcularPrecioConDescuento(precioBoleto, 50);
    cout << "Precio con promocion de martes (50%): $" << precioPromoMartes << endl;

    return 0;
}

double calcularPrecioConDescuento(double precio, double porcentajeDescuento) {
    return precio + (precio * porcentajeDescuento / 100);
}
```

Con el mismo error (`+` en vez de `-`), esta versión imprime exactamente los mismos
valores incorrectos — pero para corregirla basta con cambiar **una sola línea**, la
del `return` dentro de `calcularPrecioConDescuento`:

```cpp
double calcularPrecioConDescuento(double precio, double porcentajeDescuento) {
    return precio - (precio * porcentajeDescuento / 100);
}
```

Con esa única corrección, los tres descuentos (estudiante, tercera edad, promoción
de martes) quedan arreglados a la vez — `$64`, `$56` y `$40`, verificado
compilando. Esta es la segunda ventaja de la lista de 1.1: cuando sabes que el
descuento está mal, sabes exactamente en qué función buscar, y arreglarla arregla
los tres casos que la usan.

## Ejemplo 5 — el código se lee como una lista de pasos

Un programa que imprime un ticket de compra sencillo, con encabezado, cálculo del
total con IVA, y pie de ticket:

**Sin funciones** — todo junto en `main()`:

```cpp
#include <iostream>
using namespace std;

int main() {
    cout << "===== Tienda EIPTPL =====" << endl;
    cout << "Ticket de compra" << endl;
    cout << "--------------------------" << endl;

    double subtotal;
    cout << "Subtotal de la compra: ";
    cin >> subtotal;

    const double IVA = 0.16;
    double total = subtotal + (subtotal * IVA);

    cout << "--------------------------" << endl;
    cout << "Total a pagar (IVA incluido): $" << total << endl;
    cout << "Gracias por tu compra." << endl;

    return 0;
}
```

**Con funciones** — cada parte del ticket es un paso con nombre:

```cpp
#include <iostream>
using namespace std;

void mostrarEncabezado();
double calcularTotalConIVA(double subtotal);
void mostrarTicket(double total);

int main() {
    mostrarEncabezado();

    double subtotal;
    cout << "Subtotal de la compra: ";
    cin >> subtotal;

    double total = calcularTotalConIVA(subtotal);
    mostrarTicket(total);

    return 0;
}

void mostrarEncabezado() {
    cout << "===== Tienda EIPTPL =====" << endl;
    cout << "Ticket de compra" << endl;
    cout << "--------------------------" << endl;
}

double calcularTotalConIVA(double subtotal) {
    const double IVA = 0.16;
    return subtotal + (subtotal * IVA);
}

void mostrarTicket(double total) {
    cout << "--------------------------" << endl;
    cout << "Total a pagar (IVA incluido): $" << total << endl;
    cout << "Gracias por tu compra." << endl;
}
```

Los dos dan exactamente el mismo resultado, verificado compilando ambos con
`$150` de subtotal. La diferencia está en qué tan rápido entiendes `main()` sin leer
el resto del archivo: en la segunda versión, con solo leer `mostrarEncabezado();`,
`cin >> subtotal;`, `calcularTotalConIVA(subtotal)` y `mostrarTicket(total);`, ya
sabes qué hace el programa de principio a fin — cada nombre de función documenta su
propio paso, sin necesidad de leer su cuerpo. Nota también que `mostrarEncabezado`
y `mostrarTicket` son `void`: existen solo para imprimir, no para calcular nada. Es
la tercera y última ventaja de la lista de 1.1.

## ¿Debe una función hacer `cin`/`cout` ella misma, o solo calcular?

Nota que en el Ejemplo 1 (`mayor`, `menor`, `sonIguales`) y en el Ejemplo 4
(`calcularPrecioConDescuento`), ninguna función hace `cin` ni `cout` — solo reciben
datos y regresan un resultado. Quien lee el teclado y quien imprime es `main()`.
Esto no es casualidad: es una práctica extendida en ingeniería de software separar
el **cálculo** (la lógica pura: dado este dato, produce este resultado) de la
**entrada/salida** (leer teclado, archivos, pantalla, red).

- Las [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)
  (la guía de buenas prácticas de C++ mantenida por Bjarne Stroustrup y Herb Sutter)
  recomiendan que una función que produce un resultado lo regrese con `return` en
  vez de mezclarlo con otras responsabilidades — la regla F.20 dice explícitamente
  que hay que preferir el valor de retorno sobre parámetros de salida o efectos
  secundarios.
- El principio de diseño **CQS (Command-Query Separation)**, propuesto por Bertrand
  Meyer, establece que una función debería *hacer algo* (como `cin`/`cout`, que
  cambian el estado del programa o del mundo exterior) o *responder algo* (calcular
  y regresar un valor) — pero no ambas a la vez, porque mezclar las dos
  responsabilidades hace la función más difícil de leer, probar y reutilizar.
- El patrón **"Functional Core, Imperative Shell"** (núcleo funcional, cáscara
  imperativa) formaliza esta misma idea: toda la entrada/salida se concentra en la
  capa "de afuera" del programa (aquí, `main()`), mientras el núcleo que calcula se
  mantiene libre de I/O — así se puede probar y reutilizar sin depender de teclado,
  pantalla o archivos.

**¿Y el Ejemplo 2 (`sumaDeNNumeros`), que sí hace `cin` dentro de la función?** Es
la excepción pragmática que ya señalamos ahí: sin arreglos todavía, no hay forma
limpia de pasarle "n números" como parámetros separados. No es que la regla no
aplique — es que, con las herramientas que tenemos hasta ahora, cumplirla al pie de
la letra no siempre es posible. Cuando lleguemos a arreglos (Etapa II) vas a poder
escribir la versión que sí separa lectura y cálculo.

**Razón práctica para este curso:** si `calcularPrecioConDescuento` tuviera su
propio `cin` adentro, solo podría usarse leyendo del teclado. Cuando el curso llegue
a la Etapa IV (archivos), vas a querer calcular descuentos sobre precios que vienen
de un archivo, no del teclado — y una función que solo calcula (sin `cin` propio)
funciona igual sin cambiar una sola línea, mientras que una función con `cin`
integrado tendrías que reescribirla.

**Regla práctica para el curso:** el `cin`/`cout` va en `main()` (o en la función que
esté orquestando el programa); las funciones que escribas para calcular o decidir
algo reciben lo que necesitan como parámetros y regresan su resultado con `return`,
sin leer ni imprimir nada por su cuenta — salvo la excepción pragmática ya explicada.

## Autocheck

**¿Qué error de compilación esperarías si borras el prototipo de `mayor` pero dejas
la definición después de `main()`?**

Un error de tipo "use of undeclared identifier" (o "was not declared in this scope"),
porque el compilador procesa el archivo de arriba hacia abajo: al llegar a la llamada
dentro de `main()` todavía no sabe que `mayor` existe, ya que su definición aparece
más abajo en el archivo.

**¿Puede una función no tener parámetros? ¿Y no tener valor de retorno?**

Sí a ambas, y son independientes entre sí. Una función sin parámetros se declara con
paréntesis vacíos, `func()`. Una función sin valor de retorno se declara `void
func(...)` y no necesita `return valor;` en su cuerpo.

**Si copias y pegas por accidente una segunda función `int main() { ... }` en el
mismo archivo, ¿qué tipo de error esperarías?**

Un error del compilador ("redefinition of main"), no del enlazador — porque las dos
definiciones están en el mismo archivo y el compilador las detecta directamente al
revisarlo, antes de llegar a la etapa de enlazado. El error de enlazado ("duplicate
symbol") solo aparecería si las dos definiciones de `main()` estuvieran en dos
archivos `.cpp` distintos compilados juntos.

**¿Por qué `cout` funciona sin que tú hayas escrito su código, con solo poner
`#include <iostream>`?**

Porque el `#include` solo trae la *declaración* de `cout` (le dice al compilador que
existe y de qué tipo es) — su implementación real ya está compilada dentro de la
biblioteca estándar de C++ que instalaste junto con tu compilador. El enlazador
conecta tu llamada a `cout` con esa implementación al armar el ejecutable final,
igual que conectaría una llamada a una función tuya con su definición en otro
archivo.

**En el Ejemplo 3, ¿por qué `imprimirTabla` no necesita `return`?**

Porque su tipo de retorno es `void` — no está diseñada para producir un valor que
`main()` vaya a usar después, solo para imprimir en pantalla como efecto de haberla
llamado.

**En el Ejemplo 4, si el error (`+` en vez de `-`) estuviera en la versión "sin
función", ¿cuántas líneas habría que revisar para asegurarte de haberlo corregido
en todos lados? ¿Y en la versión con función?**

En la versión sin función, 3 líneas — una por cada descuento calculado
directamente en `main()` — y hay que revisar las 3 para confirmar que ninguna se
quedó con el error. En la versión con función, solo 1 línea: el `return` dentro de
`calcularPrecioConDescuento`, porque los tres descuentos pasan por esa misma
función.

**En el Ejemplo 5, ¿por qué `mostrarEncabezado` y `mostrarTicket` son `void` en vez
de regresar algo?**

Porque su trabajo es imprimir texto en pantalla, no calcular un valor que
`main()` vaya a usar después — son funciones que *hacen algo* (imprimir), no que
*responden algo* (calculan y regresan). Es la misma distinción de "Command-Query
Separation" que vimos más arriba para justificar por qué `cin`/`cout` van en
`main()` y no dentro de funciones de cálculo.

**¿Por qué `sumaDeNNumeros` (Ejemplo 2) sí hace `cin` dentro de la función, si la
regla general dice que no debería?**

Porque sin arreglos todavía no hay forma limpia de recibir "n números" como
parámetros separados — es una excepción pragmática dadas las herramientas que
tenemos hasta ahora, no una contradicción de la regla. Con arreglos (Etapa II) se
podría separar la lectura del cálculo.
